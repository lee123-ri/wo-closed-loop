# 指标异常处置工单 · 出参契约（v1.0.0）

> 定位：这是「可靠性 Agent 出参」与「软工单平台入库」之间的**接口契约**。
> 荣兴汉的 Agent（`wind-farm-anomaly-sop` v3.2）按此 schema 吐结构化 JSON，平台侧据此建单。
> 三个文件配套：本契约 `.md` + `workorder.schema.json`（机器校验）+ `黄金样本-泰康师宗9工单.json`（验收样例）。

---

## 1. 为什么需要这一层（问题回顾）

荣的 Agent 目前输出是 **HTML/自然语言 SMART 工单**（S/M/A/R/T prose），不是机器可读数据。
软工单平台要"自动导入 → 生成系统工单"，必须先把出参固化成**带字段类型的 JSON**。

本契约做了两件事：
1. 把 SMART 结构（S/M/A/R/T）**平铺成 OA 模板字段**（自动化入库用）；
2. 保留 `smart` 原文快照（复盘/追溯用，不丢信息）。

---

## 2. 字段映射总表

出参字段 → 内部 `WorkOrder` 列 → OA 表单字段（组件 ID）

| 出参 schema 字段 | 内部 WorkOrder | OA 模板字段（组件ID） | 导入时处理 |
|---|---|---|---|
| `title` | `title` | （工单编号=平台生成） | 标题入工单 |
| `subtype` | —（备注/细分） | 不入 OA 10 字段 | 超时/高频/共性缺陷/紧急确认，定措施模板 |
| `oa_type` | `type_id` → `WorkOrderTypeKB` | 工单类型 `DDSelectField_XQFBCVFYWUTC` | **GAP-004 待裁决**，默认「设备预警工单」 |
| `project` | `project_id` → `Project` | 项目名称 `TextField_1QGCEOMI5BKW` | 按名匹配项目 |
| `reason` | `reason` | 触发原因 `TextareaField_SG1XBBO1BTA8` | 直接落 |
| `action` + `target_metric` | `action` | 行动要求 `TextareaField_1XZUBAS9SW9HC` | action 为主，M 目标值可并入 |
| `responsible.name` | `person_id` → `User` | 责任人 `InnerContactField_KMXLJ63RDB0G` | name→userId 查表（见 GAP-2） |
| `approver.name` | `approver_id` → `User` | 审批人 `InnerContactField_35YBN4HMVKOW` | name→userId 查表 |
| `deadline_days` + `deadline_basis` | `deadline` | 截止时间 `DDDateField_ETPZKF5YE2GW` | 派发日+N 折算绝对日期（见 GAP-3） |
| `evidence` | `Attachment` | 工单记录附件 `DDAttachment_1I2YMU3UL8CU8` | EAM 原文引用，落附件/佐证 |
| `completion_criteria` | `conclusion`（闭环回填） | 执行结论 `TextareaField_1RWZPSOTPU0OW` | 闭环时回填 A 完成标志 |
| `workorder_id` | 幂等去重键 | 不入 OA | 重跑不重复建单 |

> 注：`create_oa_approval()` 现发起时只送 8 个字段（不含附件/执行结论），附件与执行结论在闭环阶段回填。

## 3. 平台侧补齐的「系统字段」（Agent 给不了，只有平台有）

> **核心原则（人工兜底）**：平台的建单流程本身有一道**人工确认/编辑步骤**（回填→措施工单表单，含 工单标题/触发原因/行动要求/责任人/截止时间）。
> 因此**不追求 100% 自动映射**：能确定映射的字段自动填；映射不确定/拿不到值的字段**留空**，由确认人在该步补填。
> 这与荣的 SOP 原则 #4「全自动化 + 管理者仅做最终判断」一致——机器给草稿 + 默认值，人做最终拍板。

| 字段 | 自动补齐规则 | 兜底 |
|---|---|---|
| 工单编号 | `RW-YYYY-NNNN` 平台生成 | —（必填，平台出） |
| 标题/触发原因/行动要求 | 出参 `title/reason/action` 直接落 | —（Agent 必给） |
| 截止时间 | `date(派发日) + deadline_days` 折算 | 折算不出 → 留空，人工填 |
| 责任人/审批人 userId | `name → User.dingtalk_id` 查表命中则填 | **查不到（如「远景能源」是组织）→ 留空 + 把 name 写进备注，人工选人** |
| 工单类型 | `oa_type` 直接落，OA 无该值则 fallback「其他」 | 人工可改下拉 |
| 附件 | evidence 文本存佐证 | 暂以文本入「触发原因」 |

## 4. 待确认项（不再是阻塞，留空+人工兜底即可）

| 项 | 说明 | 处理 |
|---|---|---|
| 工单类型归属 | 荣的 4 分型 ≠ OA 11 类 | 默认「设备预警工单」(GLZY-009)，人工可改 |
| 责任人 userId | 「远景能源」是厂家组织 | 留空 + 备注 name，人工在确认步选人 |
| 截止时间基准 | deadline_days 从哪天起算 | 按「派发日」折算，人工可改日期 |

## 5. 下一步（step 3：最短导入链路）

在 `backend/app/api/imports.py` 增加 `POST /import/agent-workorders`：
1. 入参 = 本契约 JSON；
2. 逐单：`workorder_id` 去重 → 能映射的字段自动填、映射不到的字段留空 → 建 `WorkOrder`（草稿态，不发群不派发）；
3. 进入现有的人工确认步骤，确认人补填留空字段后派发；
4. 先只验证 **1 张工单**（如 F15 变频柜PLC）真变成系统里一张单，再放开 9 张。
