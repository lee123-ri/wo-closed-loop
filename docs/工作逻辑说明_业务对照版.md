## 一、总体架构：Web 面板 + 异步任务 + 钉钉两通道

系统是一套标准的「前后端分离 + 异步任务」Web 应用，业务逻辑都在后端；钉钉承载两件事：一是 OA 审批作为工单闭环载体，二是群机器人/工作通知作为触达通道。

| 组件 | 选型 / 形态 | 职责 |
|------|------------|------|
| 前端 | Vue3 + Vite + TS + TDesign | 工作台、工单列表/新建、我的工单、数据池、SOP 知识库、规则配置 |
| 后端 API | FastAPI + SQLAlchemy 2.0 | 工单 CRUD、状态流转、数据池、审批/通知、鉴权 |
| 异步 Worker | Celery worker（`wo-worker`，2 副本） | 发送通知、执行定时扫描 |
| 调度器 | Celery beat（`wo-scheduler`，1 副本） | 定时触发 SLA 扫描 / 升级扫描 / 每日简报 |
| 数据库 | PostgreSQL 15（阿里云 RDS） | 工单、数据池、项目/人员、审批流/SLA/通知策略等 |
| 缓存 | Tair / Redis | access_token 缓存、Celery broker/backend |
| 文件 | 阿里云 OSS | 工单佐证附件 |
| 数据通道 | dws CLI（内置进镜像 + 凭证包 Secret 注入） | 读钉盘、读钉钉 AI 表格 |
| 钉钉 OA | 钉钉审批（旧版 oapi 网关） | 工单发起审批、状态回调/轮询 |

- **部署形态：** ACK 托管集群，`wo-backend` / `wo-frontend` / `wo-worker` / `wo-scheduler` 四个 Deployment + ALB Ingress；`wo-judgment-agent`（判断 Agent）在当前 k8s.yaml 中已注释、**不部署**（见第十节）。
- **当前状态：** 待上线。本机回归 39 用例全绿，剩环境事项：Docker 镜像实测 / 钉钉事件订阅 / ACK 部署。

## 二、数据源与输出一览

### 2.1 数据从哪里来（输入）

| 数据源 | 类型 | 用途 |
|--------|------|------|
| 钉盘「年度运营计划」工单版 xlsx（**定稿夹 + 初稿夹**，初稿夹=「Agent运营计划初稿（待判定会及确认工单）」33 项目子文件夹） | 钉盘文件（dws 下载） | 计划类工单来源，只导「文件名含工单版」的表、且「工单载体 = 非EAM」的行（无载体列整表按非EAM） |
| 钉钉 AI 表格「数据池-异常指标表」 | 多维表（dws aitable） | 异常类工单来源 → 数据池(anomaly) → 「信息搜集工单」 |
| 钉钉 AI 表格「数据池-计划表（异常原因表）」 | 多维表 | 「应推工单未推」的非 EAM 工单 → 数据池(plan) |
| 钉钉 AI 表格「数仓.0 映射表」 | 多维表 | 项目简称/责任人/省份→大区映射，回填本项目与区域 |
| 公司 OA「运维项目台账」网页 | 网页（Playwright 登录抓取，取法同年度运营计划机器人） | 以 OA 台账为准：按「项目状态=执行中/待执行」且名称含中文的项目名同步入本地项目表，名单外旧项目停用（`POST /config/projects/sync-ledger`；凭据走 env `OA_USERNAME/OA_PASSWORD/OA_BASE_URL`） |
| 手动录入 / CSV 上传 | 前端表单 / API | 补充录入（数据池或直接建单） |
| 群机器人 @ 指令 | 钉钉群 | 快捷建单（`@机器人 创建工单：…`） |
| 开放 API（X-API-Key） | HTTP（`/api/external/work-orders`） | 外部系统/Agent 直接建单与查询（按名称/编码解析、幂等去重、默认落「待派发」） |
| 配置文件 | `.env` + 数据库 config 表 | 钉钉凭证、OA 模板、SLA、优先级规则、审批流、通知策略 |

> 同步触发分两类：**自动轮询**——异常指标表（每 `anomaly_sync_interval` 秒增量）+ 钉盘年度计划工单版（定稿夹+初稿夹，每 `plan_sync_interval` 秒、默认 3600，导非EAM 计划工单，`source=plan` 自动进工单列表）；**手动**——AITable「异常原因表」非EAM 与全量一键（`/pool/sync-aitable`、`/pool/sync-full`）。`/pool/sync-drive` 与轮询共用同一「定稿+初稿」扫描。

### 2.2 结果到哪里去（输出）

| 输出 | 载体 | 接收方 / 落点 |
|------|------|---------------|
| 工单记录 | `work_orders` 表 | 前端工作台 / 工单列表 / 我的工单 |
| OA 审批单 | 钉钉审批实例 | 责任人（执行/提交佐证）→ 审批人（确认闭环） |
| 通知 | 钉钉工作通知（JSON 卡片）/ 群机器人 | 责任人、审批人 |
| 状态回写 | 数据池 backfill 字段、AI 表格回写 | 数据池原始记录（原因/措施/回填时间） |
| 措施工单 | 新生成的 `work_orders` 记录 | 由「信息搜集工单」判定后生成，直接派发 |
| 佐证附件 | OSS + 钉盘 | 审批单附件同步回工单 |
| 运行日志 | `status_log` / `escalation_log` / `notification_log` | 状态流转、升级、通知追溯 |

## 三、触发方式与主流程（无固定周节奏）

本系统不像定时周报类 Agent 那样按「周一/周三/周五」跑固定节奏，而是**事件驱动为主 + 定时扫描兜底**：

| 触发方式 | 触发点 | 业务侧会看到什么 |
|----------|--------|------------------|
| 手动同步数据源 | 管理员点「同步」或调 `/pool/sync-*` | 钉盘「工单版」非 EAM 行 / AI 表格异常指标进入数据池并生成工单 |
| 建单即发起审批 | 手动建单 / 数据池批量生成后 dispatch | 责任人钉钉收到 OA 审批与工作通知 |
| OA 事件回调 | 钉钉审批节点通过/驳回时推送 | 平台状态自动随 OA 结果推进，无需人工改 |
| OA 轮询兜底 | 后台每 10 秒拉取一次所有「有真实 OA 单且未闭环」的工单 | 无感；回调不稳定时仍能同步最新状态 |
| 定时 SLA 扫描 | 每 5 分钟 | 到期前 24h 预警、已逾期标红并通知 |
| 定时升级扫描 | 每 10 分钟 | 逾期 ≥1/3/7 天逐级升级 |
| 每日简报 | 每天 9:00 | 群机器人发当日活跃/逾期/即将到期汇总 |

## 四、各核心模块详解（输入 / 处理 / 输出）

### 4.1 计划类工单来源：钉盘「工单版」非 EAM 行（drive_workorder_import.py）

| 项目 | 说明 |
|------|------|
| 触发 | 自动轮询（定稿夹+初稿夹，每 `plan_sync_interval` 秒）+ 手动 `/pool/sync-drive`（或 `/pool/sync-full`） |
| 输入 | 钉盘「定稿夹」+「初稿夹（Agent运营计划初稿）」内各项目的「工单版」表；项目表；用户表 |

**处理逻辑：**

1. 递归列举「定稿夹 + 初稿夹」两个 alidocs 文件夹，只收文件名含「工单版」的表（初稿每项目有视觉/汇报/文档/工单版 4 类，其余 3 类不扫）；**不回退关键词搜索**（防初稿静默污染）。
2. 下载 xlsx，按表头自适应解析（兼容「工单型」与「资管型」两套列结构）。
3. **EAM / 非EAM 过滤（关键口径）：** 有「工单载体」列 → 只留「非EAM」行（EAM 交给既有 EAM 系统）；**没有「工单载体」列 → 整表按非EAM 导入**（2026-09-03 业务拍板）。
4. **按文件名匹配项目：** 项目简称是文件名子串即命中（最长匹配优先，初稿文件名形如「260818中建投景县煜特工单版」）；匹配不到再看 R1 标题行兜底。
5. 去重后建单：`source_code=plan`、状态 `pending`（待派发，后续走 OA 审批），责任人按表内「负责角色/责任人」匹配，缺失则标注「责任人待确认」。

**输出：** 计划类工单（pending，自动进工单列表）；跳过的文件及其原因（供项目侧补齐「工单载体」列 / 文件名加项目名）。

### 4.2 异常指标工单来源：AI 表格 → 数据池 → 「信息搜集 → 回填 → 判断 → 措施工单」（aitable.py + pool_service.py）

| 项目 | 说明 |
|------|------|
| 触发 | 手动 `/pool/sync-aitable` 同步到数据池；`/pool/generate` 生成工单 |
| 输入 | 「数据池-异常指标表」（每条记录 = 一个异常事件）；「数仓.0 映射表」 |

**处理逻辑：**

1. 同步「异常指标表」→ 数据池（`pool_type=anomaly`），每条异常生成一条「信息搜集工单」素材。
2. 同步「映射表」→ 回填项目/责任人/区域（省份自动归一化为华北/华中/华东/华南/西北/西南/东北大区）。
3. 数据池生成工单时：异常类固定 **P1**、`source_code`=对应异常大类 code（即 `metric_type`，8 类之一）、状态 **pending**；责任人按「异常大类默认责任人 → 区域 PMO → 异常表整改人」三级解析（大类默认责任人见 10 类工单类型规则配置，后台 `/config` 可改，当前异常类默认金惠良、双细则默认徐林杰）。
4. **大类归类（Phase 1 新增）：** 同步时按「异常指标」原文自动归入 8 大类——发电量异常/限电量异常/双细则异常/设备可靠性/信息化使用/应签未签/成本费用/客户满意度，落 `metric_type`（分类逻辑 `services/metric_types.py`，每类对应不同默认责任人 + 后续各自的分析 Agent）。
5. **回填：** 责任人在「我的工单」填写「根因分析 + 应对措施」，异常工单（`metric_type` 非空）回填后进入五阶段①「分析结果确认」（`status=judging`、`alert_phase=confirming`）。
6. **五阶段闭环（异常主单，alert_phase 细阶段）：** ① 分析结果确认（`confirm_analysis`：把措施草稿建成 `pending` 措施工单并多对多挂载到 `work_order_measure_links`，措施工单 `source_code` 继承主单 `metric_type`）→ ② 派发工单（`dispatch_measures`：逐个发起 OA 派发，主单进 `tracking`）→ ③ 已派工单·跟踪（每条措施闭环回写主单 `2/11` 进度，全闭环自动置「待复核」）→ ④ 指标复核（`reexamining`；指标仍异常可 `redispatch` 手动补派发回 ③）→ ⑤ 指标恢复闭环（`confirm_recovered`：`closed`+`recovered`；或「无需措施直接闭环」）。同类异常支持 `reuse`（挂载复用现有措施工单）/`merge`（合并进同项目同类的开着主单，发生记录迁入 `anomaly_occurrences`）。

**输出：** 数据池记录（含回填原因/措施）、信息搜集工单、措施工单；回填数据可写回 AI 表格原始记录。

### 4.3 工单流转 + OA 审批闭环（approval_engine.py + oa_event.py + oa_poller.py）

**状态机（9 态，`config/system.yaml`）**

| 状态 | 名称 | 允许流转到 |
|------|------|-----------|
| pending | 待派发 | approving |
| approving | 审批中 | dispatched / rejected |
| dispatched | 已派发 | executing |
| executing | 执行中 | verifying / overdue |
| verifying | 待验收 | closed / executing |
| closed | 已闭环 | — |
| overdue | 已逾期 | executing / verifying / closed |
| rejected | 已驳回 | — |
| judging | 判断中（alert 主单；细阶段见 `alert_phase`：confirming→dispatching→tracking→reexamining→recovered） | closed（`confirm_recovered` / 无需措施直接闭环） |

> **alert 主单的「五阶段」是独立于上面 9 态状态的细阶段机（`WorkOrder.alert_phase`），不与钉钉 OA 驱动的 `status` 冲突**：主单 `status` 只保留「pending（待回填）→ judging（已回填/判断中）→ closed」，责任人/审批/执行这条链由**措施工单（`is_measure`，继承主单的异常类型 `source_code`）**走普通 OA 流转；主单在①-④阶段 `status` 恒为 judging、靠 `alert_phase` 推进，到步骤⑤才 `closed`。

**钉钉 OA 是工单状态的唯一来源：** 平台状态不靠本地直接改，而是由钉钉审批实例的实际状态推导而来，天然幂等。

**处理逻辑：**

1. 建单时（手动建单）发起钉钉 OA 审批；发起前强制校验必填字段（项目/工单类型/责任人/审批人/计划开始时间/截止时间/触发原因/行动要求），缺失即拦截.
2. **双通道状态同步：** ① 事件回调（钉钉 `bpms_instance_change`/`bpms_task_change` 推送，走 `/dingtalk/oa/callback`，验签）；② 主动轮询兜底（后台每 10 秒遍历「有真实 OA 单且未闭环」的工单拉最新状态）。两条通道落到同一套 `apply_oa_event` 处理逻辑。
3. 状态推导：**驳回/撤销 → rejected；已归档且通过（COMPLETED）→ closed；通过 1 个审批节点 → verifying**；并同步回写钉钉端改动的表单内容与佐证附件。
4. 闭环时记录完成日期、结论文案；逾期闭环则回算逾期天数。

> ⚠️ OA 审批节点数：代码内存在注释不一致（`api/dingtalk.py` 写「3 节点：审批人→执行人→审批人」，`oa_event.py` 写「实际模板 2 节点：责任人→审批人」）。**本文档以 `oa_event.py` 的状态推导为准（2 节点），真实钉钉模板节点数需与钉钉后台核对**，见第十节待核实清单。

### 4.4 通知与升级（tasks.py + notification_service.py + approval_engine.py）

**事件类型：** `dispatch`（派发）/ `unread`（未读）/ `sla_warn`（到期预警）/ `sla_breach`（违约）/ `sla_breach_72h`（严重违约）。

| 定时任务 | 周期 | 逻辑 |
|----------|------|------|
| SLA 扫描 | 每 5 分钟 | 遍历非闭环工单：距截止 ≤1 天 → `sla_warn`；已过截止 → 标 `overdue` + `sla_breach`；逾期 ≥3 天 → `sla_breach_72h` |
| 升级扫描 | 每 10 分钟 | 对 `overdue` 工单按逾期天数升级：≥1 天 L1、≥3 天 L2、≥7 天 L3，逐级抬升，不重复 |
| 每日简报 | 每天 9:00 | 群机器人发当日活跃/逾期/即将到期汇总（钉钉未配置则跳过） |

- 通知通道由「通知策略表」（数据库 config）按「优先级 × 事件」解析；当前实际生效的主要是**钉钉工作通知（JSON 卡片）**，群机器人 webhook 为占位（未配）、短信为 mock、电话 DING 简化为工作通知。

### 4.5 手动建单与群机器人（workorders.py + bot.py + external.py）

- **手动建单：** 前端表单 / API，优先级未填时按「工单类型」兜底（8 类异常→P1，否则 P2），审批人未指定时按该工单类型的默认审批人（`config_definitions.category=work_order_type` 的 `default_approver_name`）解析，截止未填时按 SLA 默认天数顺延。
- **群机器人：** 群内 `@机器人 创建工单：项目 标题 责任人 截止`，自动解析并建单（`source=manual`、状态 `pending`），回复卡片链接；限流 30 次/分钟。
- **外部 API（external.py）：** `X-API-Key` 鉴权（env `EXTERNAL_API_KEY`，为空整接口 503）。入参项目/责任人/审批人/类型按「名称/编码」解析为内部 id，**找不到即报错（404/409）、不自动建实体**；`client_request_id` 幂等去重（重试返回首次那条）；建单默认 `source=external`、状态 `pending`（待派发）、**不自动发起钉钉审批**，平台内人工派发后进 OA；另支持按 `code` / `client_request_id` 查询。详见 `docs/外部建单接口.md`。

## 五、业务口径（对照重点）

### 5.1 工单类型（10 类统一口径，2026-09-17 起）

> 来源/工单类型/异常指标大类三合一：`source_code` 承载唯一「工单类型 code」。10 内置 + 后台可极简新增（只输名字，自动 `custom_N`，走计划流）。老 `type_id`→SOP 知识库本轮不迁移。

| code | 名称 | 流程 |
|------|------|------|
| plan | 运营计划工单 | 计划流（排期 scheduled + 必填门禁 + 按月自动派发） |
| power_gen | 发电量异常工单 | alert 五阶段闭环 |
| curtailment | 限电量异常工单 | alert 五阶段闭环 |
| dual_rule | 双细则异常工单 | alert 五阶段闭环（双细则子表直导） |
| reliability | 设备可靠性异常工单 | alert 五阶段闭环（可靠性 Agent 导入宿主） |
| info_quality | 信息化使用异常工单 | alert 五阶段闭环 |
| contract | 应签未签工单 | alert 五阶段闭环 |
| cost | 成本费用工单 | alert 五阶段闭环 |
| satisfaction | 客户满意度工单 | alert 五阶段闭环 |
| meeting | 关键会议工单 | 三步闭环（判定会/领导交办/未分类兜底） |

> 8 类异常仍走五阶段闭环（`metric_type` 非空判定，`alert_phase`：confirming→dispatching→tracking→reexamining→recovered），流程不被统一类型拍平。

### 5.2 优先级（按类型定）

| 工单类型 | 优先级 |
|------|--------|
| 8 类异常（metric_type 非空） | 固定 P1 |
| 运营计划（plan） | 同步计划表自带优先级，缺失兜底 P2 |
| 关键会议 / 新增类型（meeting / custom_N） | 手填自选，未填兜底 P2 |

> 早期「正则匹配标题自动定级」的方案已废弃（规则台账确认），正则仅剩听记解析备用。

### 5.3 SLA 时限（3 档）

| 优先级 | 截止天数 | 到期预警提前 | 违约后升级 |
|--------|---------|-------------|-----------|
| P1 | 1 天 | 4 小时 | 24 小时 |
| P2 | 3 天 | 24 小时 | 72 小时 |
| P3 | 7 天 | 48 小时 | 168 小时 |

> ⚠️ 此组数值为系统自定、**无官方指引源**（规则台账已把 P1 从文档旧值 2 天统一为 1 天），需业务方最终确认。

### 5.4 升级阶梯（1/3/7 天）

| 级别 | 触发 | 动作 |
|------|------|------|
| L1 | 逾期 ≥1 天 | 预警 |
| L2 | 逾期 ≥3 天 | 升级（抄送审批人） |
| L3 | 逾期 ≥7 天 | 严重升级（升级上级） |

> 早期方案对比面板里另有「24h 前提醒 / 超期 24h / 超期 72h」一套阶梯，与代码不一致；规则台账已确认以代码的 1/3/7 天为准。

### 5.5 EAM / 非EAM 口径

- **硬工单（EAM 覆盖）**：设备操作、采购验收、缺陷录入等，由既有 EAM 系统承载，**不进本系统**。
- **工单（非EAM）**：客户沟通、关系维护、纠偏措施、非标任务、异常指标处置等，由本系统承载。
- 钉盘计划表**必须有「工单载体」列**才能区分 EAM/非EAM；缺列则整表跳过（见 `总纲.md` 数据侧跟进、第十节）。

### 5.6 去重口径

- **钉盘计划导入去重：** 同项目 + 同来源(plan) + 同标题已存在则跳过。
- **AI 表格同步去重：** 按来源 `recordId` 去重，增量同步不重复入池。
- **Agent 导入批次去重：** 可靠性 Agent 导入按「项目×异常指标×周期」批次键去重，同批重导整批跳过。
- **工单编号：** `RW-<年>-<四位序号>`，按当年已有数量递增。

## 六、可靠性与安全机制

- **鉴权收编：** 后端除 `登录 / health / OA 回调 / 群机器人` 外全路由强制 JWT 鉴权；管理员路由额外 `require_admin`。
- **行级数据范围（2026-09-17 起可后台配置）：** 谁看哪些工单由「数据范围角色」决定——人归角色、范围在 `role_data_scopes` 表内钩选。四个角色：admin（`users.role=admin`，锁死全部）、事业部 PMO（`role_assignments` 的 division_head/pmo，默认全部）、区域 PMO（`region_pmos`，默认自己相关+区域）、普通成员（其余，默认自己相关）。每角色可见范围三档可多选、取并集去重：自己相关（`person_id==本人 or approver_id==本人`）、区域（工单大区∈其负责区域，仅区域 PMO 有区域）、全部（不限）。单一来源 `app/services/scope.py`（`resolve_data_role`+`apply_scope_to_query`），`/work-orders?scope=mine`、`/work-orders/closed/list?scope=mine` 走它；范围在后台「规则配置→数据权限」或 `GET/PUT /config/role-scopes` 改（admin 锁定）。「我的工单」是另一条严格个人口径（`apply_personal_scope_to_query`，不因管理身份扩大），`/dashboard/mine`、`/dashboard/calendar?mine=true`、`scope=personal` 走它。
- **外部 API 独立鉴权：** `/api/external/*` 走独立的 `X-API-Key`（env `EXTERNAL_API_KEY`，为空则接口整体 503），与用户 JWT 解耦；密钥单点共享须走 HTTPS、泄漏即轮换。
- **钉钉 OAuth（唯一入口）+ 管理员专用：** 钉钉一键登录（code 换 token → 拉用户信息 → 匹配系统用户签发 JWT）。不自动建号：仅已有启用用户可按姓名/手机号绑定钉钉身份；`LOGIN_ADMIN_ONLY=true`（当前）时仅管理员可登录，其他人一律 403。姓名登录（无口令）与开发登录默认关闭（`NAME_LOGIN_ENABLED`/`DEV_LOGIN_ENABLED`，生产恒关），仅作应急通道。
- **回调验签：** 钉钉 OA 回调走加解密验签（token + AES Key + 企业 ID），解密 `echostr`/`encrypt`，失败返回 400。
- **幂等：** OA 状态推导只看钉钉实例现状、不看事件到达次数，重推/重复轮询不会重复推进状态；AI 表格同步按 recordId 去重。
- **限流：** 登录 10 次/分钟、导入 10 次/分钟、群机器人 30 次/分钟、health 60 次/分钟。
- **安全响应头 / HTTPS：** nginx/ALB 层 HSTS、nosniff、DENY、XSS、Referrer 加固；CORS 生产收紧单域名。
- **降级兜底：** 判断 Agent 不可达/超时/关闭 → 降级为按 PMO 原输入建工单并写降级日志；OAuth/OA 未配 key 时返回占位不报错，便于本地开发。
- **生产硬拦截：** `AUTO_SEED` 生产环境永不自动灌演示数据。

## 七、部署与发布链路（本机打包 → ACK）

1. **准备镜像：** 后端（内置 Node + dws CLI）、前端分别构建推送到阿里云 ACR。
2. **云资源：** RDS PostgreSQL 15、Tair/Redis、OSS Bucket、ACK 托管集群、ALB。
3. **注入凭证（Secret）：** `wo-secrets`（数据库/Redis/JWT/钉钉 AppKey/AppSecret/AgentId/OA 模板 processCode/企业 ID/回调地址等）+ `wo-dws-auth`（dws 个人凭证包 `dws-auth.tar.gz`，容器启动自动 `dws auth import`）。
4. **部署：** `kubectl apply -f docker/k8s.yaml`，四个 Deployment（backend 2、frontend 2、worker 2、scheduler 1）+ ALB Ingress。
5. **初始化：** 后端 Pod 执行 `alembic upgrade head` + `python -m app.seed` 一次性建表与灌种子。
6. **配钉钉回调：** OA 审批回调 `/api/dingtalk/oa/callback`、群机器人回调 `/api/bot/command`。

**运维要点：** dws 凭证 refresh token 约 30 天过期，过期后重新导出并注入 Secret 后 `kubectl rollout restart`；数据库用 alembic 双头已修复（`e001_merge_heads`）。

## 八、定时任务一览

| 任务 | 周期 | 责任 | 说明 |
|------|------|------|------|

## 十、已知边界与注意事项（诚实告知）

1. **行业通用模块未做全：** GAP 分析（`docs/GAP_ANALYSIS.md`）对比 Jira SM / ServiceNow，指出看板视图、批量操作、工单模板、报表导出、移动端等 P1/P2 补强项尚未实现；当前仅有 CRUD、审批流、权限、SLA、通知、SOP 知识库、看板导出（部分）。
2. **OA 审批节点数待核实：** 代码注释存在「2 节点 / 3 节点」两套说法，本文档以 `oa_event.py` 的 2 节点推导为准，真实钉钉模板节点数需与钉钉管理后台核对。
3. **计划类「跳过 OA」口径不一致：** `WORKFLOW_SUMMARY.md`（8/12）写「计划类跳过 OA 直接 dispatched」，但代码中钉盘 xlsx 直导是 `pending`（走 OA 审批），数据池 plan 生成才是 `dispatched`（跳过 OA）。文档与代码不符，**以代码为准**，最终口径需业务拍板。
4. **SLA/升级数值无官方来源：** P1/2/3 的截止天数、预警小时、升级 1/3/7 天均为系统自定（规则台账标注 🔴 无源），是否按此执行需业务确认。
5. **通知通道未全量生效：** 群机器人 webhook 未配（占位）、短信 mock、电话 DING 简化为工作通知；当前真正触达的是「工作通知（JSON 卡片）」。上线前置需完成钉钉后台事件订阅 + 审批数据读取权限，否则仅靠 10 秒 OA 轮询兜底。
6. **判断 Agent v1 未部署：** 异常指标的「自动判断 → 措施工单」目前是「离线桥接（导出/导入 JSON）+ 人工审核」，或降级为按 PMO 原输入直建措施工单；`JUDGMENT_ENABLED=false`。
7. **数据同步未进定时任务：** 钉盘/AI 表格同步靠手动触发，暂无自动同步。
8. **数据源侧待项目方配合：** 部分钉盘文件「工单版-运营计划」文件名无项目名（匹配不到项目）、部分年度计划表缺「工单载体」列（无法区分 EAM/非EAM 整表跳过），需项目侧重命名 / 补列。

## 十一、密级与敏感信息边界

代码与配置中包含钉钉 AI 表格 base/table ID、OA 审批模板 processCode、AppKey/AppSecret、企业 ID、回调 AES Key、dws 个人凭证包、RDS/Tair 内网连接串等敏感标识，整体定级为 **A级（绝密）**，仅限内网部署与使用。本文档为对外/业务对照的脱敏版，已隐去上述具体标识；如需具体 ID，请查阅代码仓库内 `backend/app/services/aitable.py`、`.env` 模板与 `docker/k8s.yaml`，并按绝密件管理。dws 凭证包（`wo-dws-auth` Secret）含天游续期 refresh token，属高敏物料，导出、分发、注入均须按绝密流程执行。
