# 上线前管理界面与规则治理改造设计

- 状态：已编码实现，待本机回归（pytest + build + UI 点检）
- 日期：2026-09-17
- 范围：管理看板、我的工单、宽表交互、规则配置

## 1. 背景与问题

当前系统将“管理看板”做成了指标、待办、来源、趋势、类型等信息的平铺集合。它展示了数据，但不能让管理人员按“今天要决策什么、哪里有风险、谁需要跟进”的顺序行动。

“我的工单”界面声明只展示本人相关工单，但现行后端行级范围对管理员返回全部工单、对区域 PMO 返回区域工单加本人相关工单；列表、统计和日历全部复用此范围。这与本次确认的业务口径冲突：此页仅应展示登录人作为责任人或审批人的工单。

日历只按 deadline 标点，仅返回未闭环且设置截止日的工单；没有工作量汇总、空态或计划开始事项，因而在真实数据中容易看起来“没有内容”。

工作台表格的总宽度约 1,212px；滚动容器使用卡片的 `overflow: auto`，横向滚动条位于表格底部，长列表时用户必须滚到底部才可左右滑动。

规则配置把不同目的的内容平铺：工单类型（SOP 和默认审批人）、异常指标大类（告警归类和默认责任人）、优先级规则、SLA、角色人员、审批流。界面没有说明每项是否被运行链路消费，容易造成“配置了但无效”的误解。

## 2. 已核实的运行链路

| 配置 | 是否已实装 | 实际消费位置 | 本次处理 |
| --- | --- | --- | --- |
| 工单类型 | 是 | 建单默认审批人、SOP、导入类型匹配 | 保留，改名为“工单模板与 SOP” |
| 异常指标大类 | 是，非重复 | 告警导入：按指标大类匹配默认责任人 | 保留，但移至“告警规则”，并明确它不定义工单类型 |
| 优先级判定规则 | 部分 | 智能解析、导入、机器人建单；手工/API 指定优先级时不覆盖 | 保留，标明适用入口和命中顺序 |
| 角色人员配置 | 是 | 工单类型默认角色解析为审批人 | 保留，但仅显示被模板实际引用的角色 |
| 审批流 | 部分 | 当前节点展示、逾期升级目标 | 保留为“升级路径”；不再误称为钉钉 OA 的实际审批流。钉钉 OA 的节点由模板侧配置 |
| SLA 定义 | 是 | 未填截止日时的默认期限；SLA 扫描、看板违约统计 | 保留，补运行状态与生效说明 |

## 3. 目标与非目标

### 目标

1. 管理人员在一个首屏内识别 SLA 违约、临期、高风险来源和需要跟办的工单，并能一跳到已筛选列表。
2. “我的工单”的统计、列表和日历严格使用同一个本人双角色范围：`person_id == 当前用户 OR approver_id == 当前用户`，不因管理员或区域 PMO 身份扩大范围。
3. 宽表在顶部和底部都可横向滚动，左右固定列持续可见。
4. 将规则配置按运行目的分组，并消除“审批流实际驱动钉钉 OA”的错误暗示。

### 非目标

- 不更改钉钉 OA 模板及真实审批实例；此项须另行取得模板与联调条件。
- 不删除现有配置或历史数据；先做信息架构与文案收口。
- 不改变“工单列表”与“闭环记录”的管理范围规则；仅收紧“我的工单”。

## 4. 方案

### 4.1 管理看板：改为管理驾驶舱

首屏顺序调整为：

1. **管理摘要**：在途、今日到期、已逾期、待验收、闭环率；每张卡说明统计口径并可跳转。
2. **需要处置**：按 P1、已逾期、24 小时内到期排序，显示最多 10 条；每条明确责任人、审批人、截止时间与风险原因。
3. **管理分析**：SLA 合规、来源风险、项目/区域风险排行、近六个月趋势。无有效样本时显示“暂无足够样本”，不显示伪精确指标。

保留明细只作为行动入口；移除首屏中与管理决策无直接关系的重复总数和大段来源装饰。增加项目、区域、时间范围筛选（默认全部），所有 KPI 和跳转结果沿用同一筛选条件。

### 4.2 我的工单：单一范围、双角色视图

新增私有范围函数 `apply_personal_scope_to_query`，固定为本人责任人或审批人；`/dashboard/mine`、`/dashboard/calendar?mine=true` 与 `/work-orders?scope=mine` 在“我的工单”调用场景统一使用它。管理范围函数仍供管理列表使用，避免权限能力被意外移除。

页面将显示“本人责任 / 本人审批 / 双重角色”标签与筛选器，默认“全部相关”。统计卡、列表和日历传递同一角色筛选参数。

日历展示计划开始日和截止日两类事项：开始为蓝色、截止为橙色、逾期为红色；同一天多项折叠为“+N”。月内无事项时显示明确空态与“切换月份”操作，避免空白误判为加载失败。

### 4.3 宽表横向交互

抽出通用 `HorizontalTableShell`：在表格顶部放一个与内容宽度同步的横向滚动条，底部保持原生滚动条；两个滚动容器双向同步且有防循环保护。固定左侧选择列、固定右侧操作列保持不变。键盘聚焦到表格时可用 Shift+滚轮横移；窄屏仍可正常触摸拖动。

### 4.4 规则配置：按“可执行规则”重新分组

1. **工单模板与 SOP**：工单类型、默认审批人角色、SOP。
2. **告警分派规则**：异常指标大类及默认责任人；与工单模板分开并补说明。
3. **自动判定**：优先级正则，显示“仅智能解析/导入/机器人建单生效；手工指定优先级优先”。
4. **时效与升级**：SLA 定义及当前扫描器状态；升级路径（原审批流）仅用于平台内状态展示和逾期升级目标。
5. **组织映射**：只显示以上规则实际引用的角色及其人员；无引用项不展示。

页面顶部给每类配置展示“已接入 / 未接入”和消费链路。审批流更名为“平台升级路径”，增加只读提示：钉钉 OA 节点不由此页面下发。

## 5. 数据与兼容性

- 不需要删除表或迁移历史数据。
- 如引入 `role=responsible|approver|all` 查询参数，默认 `all`，后端严格校验枚举。
- 我的工单现有管理员/PMO 扩展范围将被移除；这是本次明确的产品口径变更，需同步更新原有范围测试。
- SLA 编辑继续即时影响新建工单的默认截止日和扫描规则；不会追溯修改既有工单的 deadline。

## 7. 风险与回滚

- 风险：将“我的工单”收紧后，部分管理员习惯从该页看全局数据。缓解：管理看板/工单列表保留全局入口，并在改版首次访问提示迁移路径。
- 风险：顶部滚动条与表格尺寸不同步。缓解：用 `ResizeObserver`，并将同步逻辑隔离为可测模块。
- 回滚：本次均为前端和只读查询范围调整；保留原管理范围函数与数据库数据，回退前端版本即可恢复原界面。
