# 前端交互审查报告

- 日期：2026-09-14
- 范围：`frontend/src` 全部（18 视图 + 2 组件 + 布局/路由/状态/api/utils，约 6100 行）
- 方法：三路并行 code review + 报告人对高危项逐一回读源码核实

## 结论一句话

整体架构（Vue3 + TDesign + Pinia 收编）是健康的，菜单/路由/取值口径一致、无原生 table/modal/alert 违规；但存在 **3 个高危交互缺陷 + 约 7 个中等 + 一批小问题**，集中在「我的工单」统计卡、新建工单必填校验、approver 登录落地、工单详情页的 OA 驱动按钮与加载错误态。

## 一、高危（建议优先修）

### H1. 非 admin 审批员在 `/` 根路径触发「重定向到自身」回环
- 位置：`router/index.ts:87-93` + `menu.ts:20` + 后端 `app/api/auth.py:246`
- 现象：守卫里「根路径 → 重定向到第一个有权限菜单」这段，`firstAccessibleMenu()` 遍历 `MENU_GROUPS` 的第一项就是「工作台 / 管理看板」(path=`/`)。后端默认权限里「管理看板」对 `approver` 开放（roles 含 approver），于是 `first` 直接等于 `/`，`next("/")` 又把自己重定向回 `/`。
- 为什么怪：approver 登录后落地到 `/` 时进入这个自指向重定向——轻则 vue-router 报冗余导航、行为不可预期，重则循环卡死。executor 因无「管理看板」权限会被正确弹到 `/my`，admin 走 `isAdmin` 直接放行，**唯独 approver 受影响**。
- 修复建议：根路径 `/` 本就映射管理看板且 approver 有权访问，直接 `next()` 放行即可；「重定向到第一个可访问菜单」这段只在「当前菜单确实无权限」时才需要，并且应跳过 path 等于当前 to 的项。

### H2. 「我的工单」——「待回填」卡绑到了「执行中」的筛选与高亮
- 位置：`MyDashboard.vue:32-35`（对比同页 `20-23` 行的「执行中」卡）
- 现象：第六张统计卡显示的是 `stats.need_backfill`，但 `:class="{ on: filterStatus === 'executing' }"` 和 `@click="setFilter('executing')"` 都与「执行中」卡完全重复（复制粘贴错误）。
- 为什么怪：点「待回填」实际筛出的是「执行中」工单；而且两张卡会同时点亮。数字口径和筛选行为错位，用户看到「待回填 N 条」点进去却是执行中列表。
- 修复建议：给「待回填」建独立筛选项（若后端支持按回填状态 `need_backfill` 查询则用上），并让高亮/点击都对齐该状态值。

### H3. 新建工单：责任人 / 审批人 / 工单类型标了红星但提交不校验
- 位置：`WorkOrderCreate.vue:158-161`（校验） + 模板 `20/26/32/52/56`（红星标记）
- 现象：`submitManual` 只校验了 `title/action/deadline/project_id` 四个字段；「审批人」(approver_id)、「责任人」(person_id)、「工单类型」(type_id)、「来源」「优先级」都在 UI 上标红 `*`，却不在校验内。其中「审批人」无任何默认值兜底，可空提交，生成一张无审批人的工单。
- 为什么怪：用户照着红星填，留空审批人照样能提交，与「必填」暗示自相矛盾（违反了「对外表单必填必须拦截」的项目约定）。后续 OA 派发时才可能爆错，责任不清。
- 修复建议：`submitManual` 开头把 `approver_id`、`person_id`、`type_id` 一并纳入空值判断，缺失字段逐个 `toast.warning` 提示并 return；建议顺便给这些控件加前端必填红字联动。

## 二、中等

### M1. 工单详情：OA 驱动的标准按钮「可见但点开必被拦」，且与列表口径不一致
- 位置：`WorkOrderDetail.vue:28-35`（渲染）、`585-595`/`749-753`（拦截）、`WorkbenchTable.vue:287-295`（列表的隐藏逻辑）
- 现象：详情页 `派发/开始执行/提交佐证/验收闭环/驳回` 按 `wo.status` 无条件渲染，第 29 行只放了一条 hint 文案；真正拦截在点击之后（`oaDriven` 才弹「请去钉钉OA处理」）。而列表页对 OA 驱动订单是**隐藏**这些按钮、只留提示 + 重置兜底（`opButtons` 287-295）。
- 为什么怪：用户看到一个蓝色主按钮「开始执行」，点下去是警告弹窗，按钮形同虚设；两处页面（列表 vs 详情）口径不一致。
- 修复建议：详情页头部按钮渲染前先判 `oaDriven`，OA 驱动时只显示提示 + 「重置」兜底，不渲染必被拦截的主按钮，与列表对齐。

### M2. 工单详情 `load()` 没有错误态，异常时页面永久卡「加载中」
- 位置：`WorkOrderDetail.vue:495-531`（`load` 无 try/catch）+ 模板 `v-if="wo"` 的 else 分支
- 现象：`wo` 初值 null，模板只在 `!wo` 时显示 loading；`getWorkOrder` 一旦 404/500 抛错，`wo` 永远为 null，页面无限转圈。「合并后主单可能 404」的注释（`doMerge:745`）自称「由 load 容错」，但 load 根本没容错。
- 为什么怪：工单不存在 / 越权 / 已闭环跳转时，用户看到的是无限转圈，没有任何「不存在 / 无权限」提示。
- 修复建议：`load` 外层加 try/catch，失败置 `errMsg` 并渲染错误态（带「返回列表」按钮）。

### M3. 工单详情 `confirmAnalysis` 吞掉保存失败仍继续流转
- 位置：`WorkOrderDetail.vue:684-690`
- 现象：保存措施草稿 `catch { /* ignore */ }` 静默吞错，随后**仍然** `transition("confirm_analysis")`；头部「确认分析结果」按钮也未绑 loading/disabled。
- 为什么怪：保存没成功用户无感知，可能基于旧的/空的 `triggered_wo_tasks` 生成措施工单；连点会重复发起流转。
- 修复建议：保存失败 `toast.error` 并 return；按钮绑 `savingTasks` 做 loading + disabled。

### M4. 派发抽屉清空责任人/审批人后点确认会「写空再派发失败」
- 位置：`WorkbenchTable.vue:355-371`（`confirmDispatchDrawer`），UI 红字在 120/124
- 现象：抽屉里 `t-select` 带 `clearable`，用户可把责任人/审批人清空；`confirmDispatchDrawer` 只判断「变了才 update」，没有非空校验，会先把责任人写空（`updateWorkOrder`），再 `transitionWorkOrder("dispatch")`，后端若拦截则数据已被清空。
- 为什么怪：抽屉里明明写着「必填字段缺失会被拦截」，前端却不拦，点了要么报错、要么留一张空责任人工单。
- 修复建议：确认前非空校验 `person_id`、`approver_id`，缺失直接 toast 阻断。

### M5. Dashboard 的 ECharts 未 dispose、无 resize 监听
- 位置：`Dashboard.vue:171-205`（`initCharts`），无 `onUnmounted`
- 现象：`echarts.init` 后既不 dispose，也不注册 `window.resize` 重绘。
- 为什么怪：反复进出看板页面会逐次累积 chart 实例（内存泄漏）；窗口缩放时图表不重绘、比例失真。
- 修复建议：chart 实例存 ref，`onUnmounted` 里 `dispose`；加 `window.addEventListener('resize', …)` 调 `resize()`，卸载时移除监听。

### M6. Dashboard / 多个列表页：接口失败被渲染成「空数据」或只有 console
- 位置：`Dashboard.vue:207-213`（失败显示「暂无工单」引导文案）、`ProjectManage.vue:104-110`、`UserManagement.vue:223-232`（`console.error` 吞错）、`AuditLog.vue:55-61`（无 loading + 静默）
- 现象：统计/列表加载失败时，用户看到的是「系统已就绪，去新建第一条工单」这类空态引导，或一张空表无任何提示。
- 为什么怪：后端挂了和「真没数据」无法区分，误导用户。
- 修复建议：统一加 `error` 状态区分「空数据」与「加载失败」，失败给错误态 + toast + 重试。

### M7. ConfigPage 多处写操作无 loading 守卫、无 try/catch
- 位置：`ConfigPage.vue` 的 `saveType/adopt?/delType/delPriority/togglePriority/saveSla` 等
- 现象：保存/删除/启禁切换无 loading/disabled，删除与 SLA 保存失败分支缺失。
- 为什么怪：双击「保存」重复创建；删除/保存失败抛未处理 rejection 且无 toast，用户以为成功（尤其 `saveSla` 失败时安静无比）。
- 修复建议：统一加 `submitting` loading + disable，失败统一 `toast.error`。

## 四、额外观察（非 bug，但值得统一口径）

- **原生控件残留**：`WorkOrderCreate` 表单（`<select>/<input type="date">/textarea`）、`DataPool` 筛选区、`WorkOrderDetail` 派发弹窗的原生 `<select>`，与项目「收编到 TDesign」的方向不一致，建议逐个换成 `t-select/t-input/t-date-picker`。这些不违反「禁用原生 table/modal/alert」的硬约定，但视觉割裂。
- **alert 主单字段口径**：`WorkOrderDetail` 里 `wo.status` 与 `wo.alert_phase` 混用做渲染/流转判断，构成多处潜在错位，建议下一轮单独做一次「状态 vs 阶段」口径核对。
