# PMO mini 私聊未回复与工单机制误答修复 V0.1.2

## 已确认的三处问题

1. 原话“现在你对问题的处理机制和升级机制是什么？”确实进入本机，但因缺少显式工单关键词被静默。原始账本保留，未补发。
2. 0.1.1接纳了该句，却误解为机器人职责。用户明确这是工单预警升级问题，因此0.1.1的“能回复”不能当作回答正确。
3. 用户重发后收到的回复没有本机反馈尾注；核对时本机只有原始静默记录，没有第二条入站，不能认领另一端回复。官方协议说明多个Stream连接随机选通道；两端并行不能保证本机接到每条消息。

## 修复与验收边界

新增sla_policy业务意图，读取当前SLADefinition及启用的followup_nodes；代码不调用扫描、通知或业务写入。保持稳定账号绑定、群项目授权和只读事务。空节点不回退旧提醒时长；无效配置说明不完整；不输出原始群ID或人员账号。纯职责问法与业务升级问法分开，混杂无关任务保持静默。

真实原话的链路回归要求出现数据库处理时限和预警升级事实，且查询实际被调用；仅出现“处理/升级”不算通过。先执行新断言确认旧版本失败，再修改。增加独立库的配置变化、禁用节点、空节点、无效节点、身份及群授权检查。真实配置只读回放使用受控本地发送器，未向钉钉测试性发送；不等同真实客户端收件验收。

## 当前业务核对（2026-10-23）

- P1/P2/P3默认截止天数为2/3/7，仅影响未填写截止日的新工单。
- 三档均配置截止前3天、前1天、当天的群汇总卡片，等级为0；没有逾期正偏移或更高等级通知节点。
- legacy check_escalation按逾期1/3/7天记等级1/2/3并写日志，函数没有通知上级动作。等级记录不能证明升级通知已发出。
- 本机兜底SLA扫描以notify=False调用，等级扫描与通知应分开。运行中的worker/beat使用deadline_cards调度范围，不能按源码full调度定义断言所有任务都在运行。
- 09:00截止卡片有来源及状态范围；10:05日通报是另一条任务。本次未更改这些业务配置或触发通知。

## 时间线与5 Whys

原始私聊静默 → 定位关键词门禁 → 0.1.1改为帮助答复 → 用户澄清业务含义 → 加强断言复现误答 → 0.1.2实时配置查询 → 独立库、真实只读链路及运行状态核验。

1. 为什么没回复：前置门禁拒绝了真实提问。
2. 为什么拒绝：只依赖显式业务词或已有上下文。
3. 为什么修完仍偏题：把“你”的指代直接推断为机器人自身职责。
4. 为什么原回归漏检：只断言有处理/升级字样及回复数量，没有断言业务事实来源。
5. 为什么还无法稳定验收：未事先验证同机器人多连接的随机分发语义，误把风险局限于重复回复。

## 行动与回滚

保留用户原话、同义业务问法、纯能力问法、无关混合问法、配置变更和无节点的回归。保持旧接收端不动；当前连接仍受随机分流限制。独立入口需用户确认后另行创建；本次没有扩大机器人身份或外发范围。回滚只回退本机代码并重新加载，保留策略和账本，旧消息不重放。

协议依据：[钉钉Stream协议描述](https://open-dingtalk.github.io/developerpedia/docs/learn/stream/protocol/)，负载均衡问答说明每次推送随机选择一个通道。
