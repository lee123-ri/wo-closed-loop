# OA 双向同步与年度运营计划按月派发改造设计

- 状态：已确认，实施中（2026-09-17 后端+前端已落地，待本机回归）
- 日期：2026-09-17
- 范围：钉钉 OA 审批状态同步、年度运营计划工单完整性、任务目标交付物、按计划开始日自动派发

## 0. 已拍板口径（2026-09-17，覆盖后文不一致处）

1. **按月自动推任务：现在实现**。每月 1 日 09:00（本地时间，celery timezone=Asia/Shanghai）自动发起「计划开始日落在当月」且必填完整的计划工单 OA；工单级幂等，历史导入先排 `scheduled`、不自动补发旧单。
2. **退回(redirect)不新增 returned 状态**。OA 表单状态与平台状态一一对应：退回就回退到当前活跃节点对应的状态（退回责任人 → `approving`；退回审批人 → `verifying`）。钉钉表单是快照不可改，修订后重提新实例（schema/幂等已支持，历史同步记录本轮未建表）。
3. **存量不完整计划工单先不动**，上线前统一清洗；完整性门禁只拦新导入/新派发。
4. **「任务目标交付物」对计划类进列表必填**，其他来源不强制；作为 OA 表单字段 + 详情页展示。本轮**不做** `evidence_pending` 附件闭环硬门禁（后文 §3/§4.1 该态暂缓）。
5. 后文 §3 状态表里的 `returned` / `blocked` / `evidence_pending` 三项本轮不引入，以本条为准：退回用活跃节点回退、缺项不建单（不落 blocked）、闭环仍走 OA `COMPLETED`。
6. **「年度运营计划」＝`source_code=="plan"` 只有钉盘「工单版」xlsx 一条来源**（`drive_workorder_import.py`）。AITable「数据池-计划/异常原因表」(`sync_non_eam_to_pool`) 映射后是 `source_code="manual"`，且表内无「交付物」列，**不纳入交付物门禁**（用户拍板）。

## 1. 结论与当前缺口

### 1.1 已具备的能力

1. **OA → 平台**：HTTP 回调、钉钉 Stream 事件和 10 秒主动轮询均调用同一状态同步函数；后两者可作为回调失败的兜底。
2. 同步以钉钉审批实例查询结果为准，不以重复事件计数推进；责任人节点通过后置为 `verifying`，审批实例 `COMPLETED` 后才置为 `closed` 并回写附件。
3. 已经关联真实 OA 实例的工单禁止平台手动流转，避免两边状态分叉。

### 1.2 不能宣称已完成的能力

1. **平台 → OA 不是持续双向同步**：平台目前只在首次派发时创建 OA 实例。此后编辑平台的标题、责任人、日期、原因或行动要求，不会改写已创建的钉钉 OA 表单；钉钉审批表单是快照。
2. **退回修改未处理**：钉钉查询会返回 `redirect`，当前实现只识别 `agree`、`refuse`、终止和完成。退回事件会留在原本状态，用户不能识别“需要修改并重提”。
3. 代码注释仍描述“三节点”，实际同步和测试均按“两节点”运行，运维和模板配置有漂移风险。
4. 年度运营计划导入当前允许空责任人、审批人、类型、计划时间等字段；重复导入只补日期，不能补全 OA 必填信息。

## 2. 目标与边界

### 目标

1. 钉钉 OA 的进行、退回、拒绝、完成状态在 10 秒轮询或事件到达后同步到平台；平台状态日志保留 OA 节点、退回意见和发生时间。
2. 年度运营计划来源（`source_code=plan`）进入主列表前，OA 发起必填项和“任务目标交付物”必须完整；其他来源仍沿用现行宽松建单规则。
3. 年度运营计划工单按 `planned_start_date` 自动创建 OA 审批实例，不再由人员逐条选择“派发”。
4. OA 拒绝保持终态；OA 退回采用 `returned` 状态，修订后创建**新的** OA 实例，不试图编辑旧实例。

### 非目标

- 不尝试把平台字段直接回写到已发起的钉钉 OA 表单；该表单由钉钉审批实例管理，正确实现是重提新实例。
- 不自动发送钉钉聊天、群消息或邮件。
- 不为 EAM 工单建立此自动派发路径；年度计划导入仍严格只取“非 EAM”。

## 3. 状态机与双向同步契约

| 钉钉实例实际状态/结果 | 平台状态 | 平台动作 |
| --- | --- | --- |
| NEW / RUNNING，尚未通过责任人节点 | `approving` | 保留当前实例；同步表单内容、附件和节点信息 |
| RUNNING，责任人节点 `AGREE` | `verifying` | 记录“已提交佐证，待验收” |
| RUNNING，`redirect` 或退回上一节点 | `returned` | 记录退回节点/意见；旧实例保留为历史，不可编辑 |
| TERMINATED / CANCELED / `refuse` | `rejected` | 终态，记录拒绝原因 |
| COMPLETED / `agree`，且交付物附件合格 | `closed` | 写闭环日期、回填结论及佐证附件 |
| COMPLETED / `agree`，但交付物附件缺失或不合格 | `evidence_pending` | OA 已完成但业务未闭环；提示补交，附件合格后才可闭环 |
| `returned` 经管理员修订并重提 | `approving` | 新建 OA 实例，保存新 `oa_id`；旧实例 ID 写入 OA 同步历史 |

新增 `oa_sync_records`（或等价 JSON 历史表）记录每次 OA 实例 ID、状态、节点、结果、意见、原始同步时间和是否当前实例。`work_orders.oa_id` 始终只指向当前实例，满足轮询查询效率；历史不可丢失。

“实时”定义为：正常事件订阅/Stream 近实时；任何漏事件在 10 秒轮询内收敛。生产多副本下轮询改为 Celery Beat 单任务，或用 Redis 分布式锁，避免每个 API Pod 同时轮询同一实例。

## 4. 年度运营计划字段与导入规则

### 4.1 新字段

在 `work_orders` 新增 `task_deliverable`（Text，中文名“任务目标交付物”）。它描述闭环时必须上传的附件/成果，不等同于执行结论；在 OA 表单、详情页、列表展开项和导入错误报告中展示。

本次不假定拥有钉钉 OA 模板管理员权限。因此系统不宣称能改变钉钉原生“审批通过”的规则：只有管理员在模板中把附件控件设为必填时，钉钉端才可提交前强制。无该权限时，平台执行独立的业务闭环门禁：OA 实例完成但未同步到至少一个交付物附件，工单进入 `evidence_pending`，不计入已闭环、不触发后续闭环动作；补交并同步附件后才转 `closed`。

### 4.2 `source_code=plan` 的完整性门禁

年度运营计划工单的以下字段不得为空：

| 字段 | 来源或补全方式 |
| --- | --- |
| 标题 | 年度计划工单名称/详细措施 |
| 项目、区域 | 已匹配的项目主数据（区域只允许七大区） |
| 工单类型 | 导入映射或年度计划默认模板 |
| 责任人、审批人 | 导入列精确匹配用户；审批人可由类型默认角色解析 |
| 触发原因、行动要求 | 年度计划的目标/问题及措施 |
| 计划开始时间、截止时间 | 明确列优先，时间窗口解析兜底；不能只填一个 |
| 任务目标交付物 | “交付物/验收/任务目标交付物”列 |

导入器先完成解析、项目/人员/审批人/类型映射和字段校验，再写数据库。任一必填缺失时：

1. 不创建 `work_orders` 记录，确保列表内不存在半成品；
2. 返回“文件名 + 行号 + 原编号 + 缺失字段”的结构化异常；
3. 记录到可重试的导入异常表（保存来源引用与原始行摘要，不保存业务附件）；
4. 同标题重导入时仅在**空字段被补齐且值通过校验**时更新；已发起 OA 的工单不覆盖，改走“退回后修订再重提”。

其他来源（manual、alert、meeting、external）不增加上述导入强制项；它们仍在真正发起 OA 前由现有 OA 必填校验拦截。

## 5. 按月自动派发

年度计划导入成功后不立即发 OA，而是进入新增状态 `scheduled`（已排期）。每月 1 日 Asia/Shanghai 09:00 执行一次派发任务：

1. 选择 `source_code=plan AND status=scheduled AND planned_start_date` 落在当月的非 EAM 工单；
2. 再跑年度计划完整性校验；缺字段转为 `blocked`，写明缺项，绝不带空字段发起 OA；
3. 合格工单统一创建 OA 实例，成功后置 `approving`；失败保持 `scheduled` 并记录失败原因，下一轮按有限重试策略处理；
4. 任务具有幂等键（工单 ID + 当前派发批次），并检查真实 `oa_id`，避免 Beat 重启或多副本重复创建审批；
5. 每月首日输出当月待派发/已派发/被阻断数量到运行日志和管理 API，不外发消息。

“按月”以计划开始日归属月份为准：6 月 1 日 09:00 自动发起所有计划开始日在 6 月的合格任务，不会在 1 月一次性把全年 12 个月任务全部推给责任人。对于历史日期的初始导入，默认 `scheduled`，首轮只生成“待补齐/待确认批次”，须由管理员显式启用自动派发，防止上线当天补发大量旧任务。

## 6. 迁移与兼容

1. 新 Alembic 迁移在线性现有 head 后新增：`task_deliverable`、OA 同步历史表、必要的状态/索引；合并前执行 `alembic heads`，必须只有一个 head。
2. 历史 `plan` 工单不直接删除：执行一次只读审计，产出缺项清单；完整记录改为 `scheduled`，不完整记录改为 `blocked`，保留状态日志。
3. API 对 `returned`、`scheduled`、`blocked`、`evidence_pending` 增加明确展示文案；前端仅对 `returned` 显示“编辑并重新发起”，对 `blocked` 显示缺项，对 `scheduled` 显示计划开始日，对 `evidence_pending` 显示缺失交付物。
4. 钉钉模板增加“任务目标交付物”展示文本，并将实际审批节点数/名称固化为配置和验收项，删除代码内不准确的三节点注释。若后续获得模板管理员权限，再把附件控件设为必填；这属于 OA 管理后台配置，非本系统代码可替代。

## 8. 已确认业务口径

1. 自动派发采用**每月 1 日 09:00（北京时间）**，统一派发当月计划开始的合格任务。
2. 年度运营计划“任务目标交付物”按“至少上传一项符合描述的附件”作为平台业务闭环硬门禁。
3. 当前不假设有钉钉 OA 模板管理员权限；钉钉原生审批无法由本系统代码强制附件必填，平台以 `evidence_pending` 守住闭环口径。

实施顺序：迁移 → 后端状态/校验/调度 → 前端 → 四层测试 → PR。
